The security correction

You rejected options (a) and (c) and approved option (b): move phone verification back into otp_challenges, keep every existing control, and let Better Auth mint the session afterwards. That is what was built.

What was wrong

Better Auth's phoneNumber plugin wrote the code into verification.value as <code>:<attempts>, in the clear. Anyone who could read that table — a backup, a replica, a leaked dump, a support tool, an SQL-injection foothold — could sign in as any user with a code in flight.

The one thing that made this harder than a config change

The plugin has a verifyOTP hook, so verification could have been delegated to us while leaving the plugin mounted. That would not have been enough: its send route writes the plaintext row before it ever calls the sender, and there is no hook on that path. Declining to call the route would have left POST /api/auth/phone-number/send-otp reachable by anyone, minting plaintext codes on demand.

So the plugin is not installed at all. Removing it removes the endpoint:

$ curl -o /dev/null -w '%{http_code}\n' -X POST \
    localhost:3000/api/auth/phone-number/send-otp -d '{"phoneNumber":"+227…"}'
404

What replaced it

An Afrinext plugin with two endpoints, /phone-otp/send and /phone-otp/verify, served through the same auth handler so they keep the same origin checks and cookie handling. Between them sits otp-store.ts, and beneath that the pure functions that were already there and already tested.

Why a hash was not enough on its own

This is the part worth arguing with me about

Your requirement said "only code_hash is persisted". The table already had that column, and Phase 0 filled it with a salted SHA-256. That would have satisfied the letter of the requirement and still been broken: a six-digit code carries about twenty bits of entropy, so an attacker holding the table and the phone number tries all 1 000 000 candidates in milliseconds. Salting stops a shared rainbow table. It does not stop a loop.

So the hash is now HMAC-SHA256 under a key derived from the application secret by HKDF, with its own domain label so it is never the same bytes as the session secret. The key is the one thing a stolen database does not contain. Rotating the secret invalidates only codes with under five minutes to live.

I made this change without asking because I read it as the difference between satisfying the decision and delivering it. If you disagree that it was in scope, that is the one judgement call in this phase I would most want corrected.

Three properties the database enforces, not this code

PropertyHowWhat it stops
One live challenge per identifier and purposePartial unique index where consumed_at is nullBanking several codes and spending each one's attempt budget — 5 guesses becomes 25
The attempt counterupdate … where attempts < max_attempts returningTwo simultaneous guesses both reading "4 used" and both proceeding
Single useupdate … where consumed_at is null returningSeveral requests presenting the same correct code all getting a session

Each of those was written in SQL rather than TypeScript for the same reason the ledger invariants were: a read-then-write that two requests interleave is not a control, and a future service in another language would have to reimplement it correctly.

What every failure says

Wrong code, expired code, exhausted attempts, and "no such challenge" all return an identical 400 auth.otp_invalid. "This number has a code in flight" is itself worth hiding, so the endpoint cannot be used to work out which numbers have accounts. The real reason goes to the audit log, where only we can read it. Tested — the two responses are compared field by field.

Migration 0006

-- 'sign_in' was forbidden while Better Auth owned the flow. It is ours again.
ALTER TABLE otp_challenges DROP CONSTRAINT IF EXISTS otp_purpose_step_up_only;
ALTER TABLE otp_challenges
  ADD CONSTRAINT otp_purpose_valid
  CHECK (purpose IN ('sign_in', 'verify_identity', 'step_up'));

-- One live challenge per identifier and purpose. Enforced here rather than in
-- application code because the alternative is a read-then-write that two
-- simultaneous requests interleave: both see no live challenge, both insert,
-- and the caller ends up holding two codes with a full attempt budget each.
CREATE UNIQUE INDEX otp_one_live_challenge
  ON otp_challenges (kind, identifier, purpose)
  WHERE consumed_at IS NULL;

Plus a table comment recording what code_hash is and why, and the auth.otp_policy settings row. The migration is idempotent on the constraint drop, so it applies to a database that already went through Phase 1 as well as to one built from zero. Tested — both paths were run.

One thing a reviewer should check me on

0006 has no drizzle-kit snapshot, the same as 0001 and 0005: it is hand-written SQL for constraints, indexes and comments, which drizzle-kit does not model. It applies and replays correctly — CI proves that on every run by rebuilding from zero — but it will not appear in a generated diff. If you would rather every migration be generated, say so and I will restructure how the invariant migrations are produced.

Together those bound guessing at 25 attempts per phone per hour against a million-value space, and the attempt budget is spent by wrong guesses whether or not they land.

The production-tuning point, as you asked

The per-IP limit of 20 per hour is the number to watch. Carrier NAT and shared connections are the norm in Niger, so a whole neighbourhood can sit behind one address and hit that limit legitimately. It is a platform_settings row — changing it is an UPDATE, not a deploy — and the caveat is written into the setting's own description so whoever finds it in the admin console reads the reason.

Financial

Untouched by the correction

The ledger, the money primitives and the commission engine have no diff in 06c9a23. You said not to weaken or rebuild the ledger; the honest evidence for that is that its files do not appear in the change at all, and the reconciliation gate still runs clean.

Commissions are configuration, resolved by rule

No rate is a constant anywhere. A rule may name a country, a category, a store, or none, and resolution is most-specific-first with a total order so the same inputs always give the same answer and a settlement can be re-derived years later. If no rule is in force, freezeSchedule throws rather than defaulting.

Decision 4, recorded where it will be seen

The seeded rates — 18 % course and digital, 15 % service, 12 % physical — are demonstration and configuration values. They are not commercial pricing and must be explicitly confirmed before the first real sale. They will be in the database from that sale onward, so the confirmation is a real gate, not a formality.

Referral, as ruled

Single level. A referral line is declared basis: { line: "platform" } with deductFrom: "platform", so it is arithmetically incapable of touching the gross customer payment or the seller's entitlement, and it cannot exceed the commission because it is a proportion of it. Nothing pays for registration or recruitment — there is no code path that would.

The residual rule

Every non-seller line rounds half-up; the seller receives gross − Σ(other lines), absorbing the remainder so the split always re-sums exactly. In XOF this is not academic: zero decimals means the minor unit is the franc, and a one-unit rounding error is a franc that either exists or does not.

The reconciliation gate, run on this commit

  "checkedAccounts": 8,

Ledger reconciliation clean over a real capture → settlement → payout cycle.

10 000 XOF at 18 % gives the platform 1 800, of which a 10 % referral takes 180, leaving 1 620 — and the seller 8 200, unchanged by the referral existing. Tested in CI as the last step of every run.

Still deliberately absent

No screen, field, API response or column calls a seller balance a deposit or protected funds. /api/v1/wallet says so in the payload itself: "Balances are contractual entitlements against Afrinext, not deposits."

Testing the tests

You asked for the correction to be tested adversarially. Twenty-three tests that all pass proves nothing on its own — a test can assert a property it does not actually exercise. So each critical guarantee was broken on purpose to see whether its test noticed.

2The attempt counter stops being bounded — drop and attempts < max_attempts1 testNOT caught cleanly
3Store the code instead of its hash7 testscaught
4Re-mount Better Auth's plaintext phone plugin1 testcaught
Two of the four slipped through, and why that matters more than the two that did not

Mutation 1 passed because the test signed in a new phone number each time, so the unique constraint on the credential row rejected the duplicate sessions. The test was passing on the strength of a completely different mechanism. Fixed by adding two tests: one below the endpoint entirely, where nothing else can intervene, and one for a phone that already has a credential.

Mutation 2 was "caught" only in the sense that something threw — but what threw was the check constraint, producing a 500 rather than the clean 400 the real code returns. The test asserted "rejects", which both behaviours satisfy. Fixed by asserting the status and the error code, which distinguishes a refusal from a crash.

Both fixes were verified by re-running the same mutation and watching the test fail. If I had stopped at "23 tests, all green", the packet would have claimed a guarantee that one of its two central tests was not actually checking.

The mutations are not committed — they were applied, run, and reverted. Section 15 shows you how to reproduce any of them in about a minute.

The deadlock the concurrency tests found

Carried forward from the first issue of this packet, because it remains the most valuable thing the phase produced and nothing about it changed.

postTransaction updated cached balance rows in whatever order the entries happened to be written, so a transfer A → B locked A then B while a concurrent B → A locked B then A. Each held what the other wanted; PostgreSQL aborted one with a deadlock. Under a real marketplace this is not exotic — two buyers paying two sellers who also trade with each other is enough — and it would have appeared as intermittent, unreproducible payment failures.

// Sorting by account id means every transaction in the system acquires these
// locks in the same order, which makes such a cycle impossible. Found by the
// concurrent-posting test, not by reasoning.
const orderedDelta = [...delta].sort(([a], [b]) => (a < b ? -1 : a > b ? 1 : 0));
Concurrency suiteBeforeAfter
Wall time23 s0.9 s
Outcomedeadlock aborts, retriesclean

The rule is in AGENTS.md: anything that locks more than one row sorts first. The suite runs as its own named CI step, so a regression is attributable rather than buried in a 175-test summary.

Unresolved risks

Closed since the last packet

Risk 1 — plaintext verification codes. Resolved by the correction. Codes exist only as a keyed hash; Better Auth's plaintext path is uninstalled and its endpoint 404s; four deliberate defects were introduced and each was caught by a test.

Risk 3 — a refused request still wrote a code row. Also gone: we now generate the code ourselves, after the rate-limit check, so a refused request writes nothing at all.

Risk A — no browser test in CI

Unchanged. The 403 on the admin route is the most security-relevant behaviour in the running application and its only proof is that I ran it by hand. A refactor that broke it would ship green. Decision 2 addresses it in Phase 2.

Risk B — the OTP key shares a lifecycle with the session secret

The hashing key is derived from SESSION_SECRET by HKDF with its own domain label, so the two are never the same bytes. But they rotate together: changing the session secret invalidates every OTP in flight. With a five-minute TTL that is a handful of people retrying, which is why it was chosen over a second secret to manage. If you would rather have an independent OTP_PEPPER, it is a small change and now is the time.

Risk C — spent challenges are not pruned automatically

A consumed or expired row holds no live secret, but it does record who asked for a code and when. pruneChallenges() exists and is tested; nothing schedules it. Left unscheduled, otp_challenges slowly becomes a contact-and-activity log nobody asked for.

Risk D — the rate limiter is instance-agnostic but not instance-tested

Counters live in PostgreSQL and increment atomically, so limits hold across instances by construction. That is tested with concurrent callers against one database; it has never run against two application processes, because there has never been more than one.

Risk E — regulatory posture is unchanged and unresolved

NIF and RCCM establish company registration. They do not establish authorization for regulated payment activity, and consent does not substitute for authorization. Nothing in this phase changes that, and no screen implies otherwise. It remains outside engineering's control.

Risk F — no SMS provider, so no real users

Not a code risk; a launch risk, and the largest one open. Section 18.
