What this is, and how long it deserves

Phase 1's packet named one gap plainly: the most security-relevant behaviour in the running application — a signed-in ordinary member being refused an admin route — had no automated proof anywhere. Its only evidence was that someone had run curl by hand. A refactor that broke it would have shipped green.

This milestone closes that. It adds three browser tests and a CI job to run them. It is not the start of a UI test suite, and adding a fourth test should be a decision rather than a habit.

Suggested review time: 20–30 minutes

Read apps/web/e2e/authorization.spec.ts (164 lines) and the mutation table in section 4. Everything else here is context. No application code changed — the diff is CI, a package manifest, gitignore, and the new test files — which is the point: the tests had to fit the application as it stands, not the other way round.

The three assertions

Each runs against a production build served by next start, driven by a real browser, over a real session cookie.

#AssertionWhat it actually checks
1 Unauthenticated → 401 All three protected routes — /api/v1/me, /api/v1/wallet, /api/v1/admin/ledger — refuse with the stable code auth.required.
2 Ordinary member → 403 on the admin ledger The one that matters. Detail below.
3 The real sign-in journey completes Phone → code → wallet. Asserts the balance renders as 0 XOF and not 0,00 XOF, since XOF has no minor unit and the wrong exponent would be a 100× error. Also asserts no wording on the screen calls the balance a deposit or protected funds, and that signed out, the same route redirects.

Why assertion 2 checks three things before it checks the 403

A 403 on its own proves nothing. A broken session, an empty cookie jar, or a route that refuses everyone would all produce one. So before asserting the denial, the test establishes that the session is genuinely live and that the actor genuinely lacks the permission:

StepExpectedWhy it is there
/api/v1/me200The session resolves to a real actor. Without this the 403 could be a dead session.
permissions contain wallet.read_owntrueThe actor really was provisioned and granted member.
permissions contain ledger.readfalseThe permission the admin route needs is one this actor genuinely does not hold.
/api/v1/admin/ledger403The assertion. Code authz.denied, message naming the permission.
/api/v1/wallet200The 403 is an authorization decision, not a blanket refusal.

This shape is a direct consequence of Phase 1: two tests there passed while actually relying on unrelated mechanisms, and were only found by mutating the code they claimed to protect.

3

Two implementation decisions worth checking me on

The API calls run inside the page, not through Playwright's request context

The session cookie is marked Secure — the application sets that whenever NODE_ENV is production, which next start is. Playwright's own request context declines to attach a Secure cookie over http, so it reported 401 for a perfectly valid session.

I only noticed because the test asserts the session is live first. Without that step I would have had a green 403 that proved nothing at all. The calls now run as fetch inside the page, which uses the browser's real cookie jar on a real origin — closer to what the application actually faces, not further from it.

The sign-in test reads the code from the sender, never from the database

Since review decision 1 the verification code exists only as a keyed hash in otp_challenges. So the test reads what ConsoleSender prints — the same channel a developer uses — and no test-only code path was added to make this easier.

A property worth noticing

A browser test that could look the verification code up in PostgreSQL would itself be evidence that the Phase 1 correction had been undone. The awkwardness here is the security guarantee working.

4

Mutation evidence

Three tests passing proves nothing on its own. Each guarantee was broken on purpose to see whether its test noticed.

Deliberate defectResultWhich test
Admin route stops calling authorize() caught Assertion 2 fails; 1 and 3 still pass.
requireActor() invents an actor instead of refusing caught Assertion 1 fails; 2 and 3 still pass.
OTP verification accepts any code not caught here None of the three. See below.
The third one is the honest result, not a gap

The browser tests always submit the right code, so they are structurally incapable of seeing that property — and they should not be credited with it. I verified where it does live rather than assuming: the same mutation fails seven tests in packages/core/src/auth, including refuses a wrong code, the attempt-limit test, expiry, cross-number replay, the identical-failure test, and the audit test.

The layering is right — browser tests own authorization, the core suite owns OTP semantics — but a reader of this document should know exactly which of the two is carrying which guarantee.
