Money integrity

A price is bigint minor units plus a currency code. The exponent comes from the currencies table, so XOF's zero decimals are a row rather than a special case: when a seller types 15 000, that is 15 000 francs, and the same string in a two-decimal currency would be 15 000 cents.

GuaranteeWhere it is enforced
No float anywhere in the pathparseMoney → Money → bigint column, read back with BigInt(). There is no point at which the amount is a JavaScript number.
A paid product cannot be free or negativeThe service refuses it and the products_price_positive check constraint refuses it. A future caller bypassing the service still cannot write one.
The currency must exist and be activeForeign key to currencies, plus an explicit check — an inactive currency is not a pricing option.
Amounts survive JSONMinor units cross the API as a string, with the currency and its exponent alongside, so a client never guesses where the decimal point belongs.
The test I would point a reviewer at first

One product is priced at 9 007 199 254 740 993 minor units — Number.MAX_SAFE_INTEGER + 2 — and read back exactly. Round-tripping that through a double lands on …992. It is a deliberately absurd price whose only job is to fail loudly if anything in this path ever becomes number arithmetic.

A related accident worth keeping: JSON.stringify throws on a bigint. That forced the transport layer to state how an amount is represented instead of letting one quietly become a float.

5

A store is a scope

Creating a store grants its creator a store-scoped store_owner role, in the same transaction as the insert. Two alternatives were rejected: granting it afterwards leaves a window in which a store exists that nobody can administer, and inferring it at request time from the owner column ("the row says you, so you may") would put an authorization decision outside authorize().

The consequence is tested directly: being a store_owner somewhere is not being one everywhere. A seller who owns store A is refused when updating store B or creating a product in it, while still able to work on their own — which is the entire reason roles carry a scope.

The seller screens also check the permission to decide what to render, but that is cosmetic. The Server Action and the API route both check again before doing anything, because a hidden form is not a permission — a page can be fetched and an endpoint can be posted to directly. Section 7 is what happens when only the cosmetic check is tested.

6

The one decision I need

Who may open a store?

Phase 0 seeded store.create as a permission and gave it to no role at all, so until now nobody could hold it. That gap had to be closed to build this milestone, and closing it is a policy decision rather than an engineering one.

Granting it to member would have decided, on your behalf, that signing up makes you a seller. Instead there is now a seller global role carrying only store.create, and nothing grants it automatically. The practical consequence: today there is no self-serve path to becoming a seller — only a direct role assignment.

Three ways forward:

  • Open marketplace — grant store.create to member. Anyone who signs up can open a store. Simplest, and the most common model.
  • Manual for now — keep it as it is until there is an admin console to grant it. Safest, but blocks any real seller onboarding.
  • Gated — grant it on some verification step. Most work, and needs you to define the step.

I have not chosen. The tests grant the role explicitly, so the vertical is proven either way.

My browser test asserted that a non-seller sees no create-store form. This is the second time in this project that a test passed on the strength of a mechanism it was not testing. It is the reason mutation runs are worth the ten minutes.

8

A bug the rebuild-from-zero step caught

Migration 0007 originally created the seller role and its permission row. That worked on my development database and fails on a fresh one: migrations run before the seed, so the permissions row the foreign key points at does not exist yet.

error: insert or update on table "role_permissions" violates foreign key
       constraint "role_permissions_permission_key_permissions_key_fk"

The fix is not a workaround: roles and permissions are reference data, and the seed is where reference data is defined. The migration now creates tables and constraints only, and says in a comment why the role is not there.

This is exactly what the "rebuild the schema from scratch" CI step exists for — a schema that only ever gets migrated forward from a database that already worked hides this class of bug until the first clean deployment.

9

What the public can see

You required that the public page expose no private seller or administrative data. Two structural choices rather than a filter:

ChoiceEffect
PublicProduct is a separate type, not a filtered copy of the internal record It has no owner id, no store id, no product id, no status and no timestamps. There is nothing private to leak, because the fields were never selected.
Both visibility conditions are in the WHERE clause A draft product, or one under an unpublished or suspended store, is not fetched-then-hidden — it is never selected. Suspending a store takes its whole catalogue down without touching a product row.

An unpublished, suspended and non-existent store all answer identically: not found. Telling them apart would let a stranger enumerate which slugs are taken and which sellers are suspended. Store slugs also reserve the paths Afrinext owns — a store called admin or wallet is refused.
