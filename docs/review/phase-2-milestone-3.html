Which action, and why it had to be asked

The brief said to identify the protected action from the blueprint, and to stop rather than choose silently if it was ambiguous. It was ambiguous, so I stopped.

The line — consent establishes layer B, never layer G 		Which action requires which document. Seven kinds are seeded; the method column enumerates signup, seller_onboarding, reaccept, checkout — which implies gates exist without saying where they attach.

One candidate mattered more than the rest: gating signup would have meant modifying the Phase 1 OTP flow, which the same brief twice forbids without approval. Choosing it silently would have been a change to authentication smuggled in as a consent feature.

Decided, and implemented exactly as decided

The protected action is createStore. The document is seller_terms, alone — the one whose subject matter is the action being taken. The general terms are a signup gate, which is a different flow and a later milestone.

Publishing a store and adding products are deliberately not gated again: you cannot publish a store you were never allowed to open, so a second check would add an enforcement point to maintain without adding a guarantee. That choice is asserted by a test, not left implicit.

The gate failed open

Found while wiring it, not by a test that already existed

requireConsent asked outstandingConsents what was unaccepted and threw if the list was non-empty. But a document with no effective version in the user's locale produces an empty list — indistinguishable, to that gate, from "everything has been accepted".

So a missing translation, a document nobody published yet, or a locale with no catalogue would have switched consent off silently. Nothing would have logged. The action would simply have proceeded.

It now fails closed. Every requested kind must resolve to a version in force, or the action is refused with a distinct error:

// `outstandingConsents` can only report what it found, so a document with no
// effective version in the requested locale produces an empty list —
// indistinguishable, to a naive gate, from "everything is accepted".
const resolved = new Set(current.map((c) => c.kind));
const missing = kinds.filter((k) => !resolved.has(k));
if (missing.length > 0) throw new ConsentUnavailableError(missing, options.locale);

The two refusals are deliberately different errors, because the remedies are different. consent.required is a 451 and the person can act on it. consent.unavailable is a 503 — the person can do nothing, and an operator must publish the document. Returning 4xx there would blame the caller for our gap.

Two tests cover it: a withdrawn translation, and a version whose effective date is in the future.

Which version is being accepted acceptCurrentVersions takes kinds, never a version id, and resolves what is in force itself A client recording acceptance of a superseded version — real-looking, satisfying nothing, and leaving the gate closed for a reason nobody can see.

Both are asserted directly. One test records an old version id by hand — exactly what a client that chose its own version could do — and confirms the gate stays shut.

7

A harness gap the fail-closed test exposed

Testing that the gate refuses when a document is unavailable means taking the document away. resetData restored versions a test had added but not ones it had deleted, so that single test left every later consent check running against a database where seller_terms no longer existed — failing for entirely the wrong reason.

The fix is in the harness, not in the one test that noticed: the baseline is now restored in both directions, including re-creating deleted placeholders and undoing any shift of their effective date.

The test itself also changed, and the reason is worth recording: consent records are append-only, so an accepted version cannot be deleted — the foreign key holds it in place. Withdrawing a document in reality means making it no longer effective, which is what an operator would actually do, so that is what the test does.
