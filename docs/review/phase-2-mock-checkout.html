Payment confirmed is not financial settlement

The line this milestone stops at

Payment confirmed — a provider event, verified against the raw bytes we received and cross-checked against our own order, says a charge succeeded. That moves the payment, moves the order, freezes the commission split, and grants the buyer's entitlement.

Financial settlement — ledger postings that turn a captured payment into a seller's claim on money. Not performed. Not by this code, and deliberately not by a mock.

Why nothing is posted to the ledger

The obvious implementation would post the capture leg — external_customer → psp_clearing — the moment a payment confirms. I did not, for three reasons, and a test asserts the absence rather than leaving it to a comment:

  • The ledger is append-only. A posting that says "a customer paid 15 000 XOF" when a mock invented the payment is a false entry in a book that cannot be corrected by deletion — only by a compensating transaction that also has to be explained. The browser suite alone would write a dozen of them.
  • A capture is a claim about the outside world. Afrinext does not observe it; a provider asserts it. Recording the assertion as a movement of value conflates "iPayMoney told us" with "the money exists", and those separate the moment a provider has an incident.
  • A seller entitlement before the funds arrive is a promise the balance cannot keep. Splitting the gross into seller and platform shares creates a claim on money Afrinext does not yet hold, in a system whose whole point is that account_balances is a cache of something true.

What confirmation does write

The frozen fee schedule. fee_schedules and fee_lines were built in Phase 1 with a comment saying subject_type would be 'settlement' now and 'order' once orders existed; orders now exist, so it is 'order'. The rows are append-only and must total the gross, so the sale's economics — 15 000 XOF gross, 2 700 platform, 12 300 seller — are permanent from the moment of confirmation. Change the commission rule next quarter and this order still says what it said today.

It moves no money. It records what the sale charged, so that settlement — whenever it is built — reads a frozen decision instead of re-resolving rules that have since changed.

The state machines, declared once and enforced twice

Both machines live in orders/state.ts as data. Not as if chains at the call sites: a transition rule expressed in three places is a rule that will eventually disagree with itself.

OrderMay becomeMeaning
pending_paymentpaid · failed · cancelled · expiredCreated and priced. The only non-terminal state.
paid—A provider confirmed a capture. Not "the seller has been paid".
failed—Terminal on purpose: a new attempt is a new checkout, with a fresh price read and a fresh expiry. Reusing an order across attempts is how a stale price gets charged.
cancelled · expired—Closed without payment.
PaymentMay becomeMeaning
initiatedpending · failed · cancelled · expiredThe row exists; the provider has not answered.
pendingsucceeded · failed · cancelled · expiredA charge is in flight. The order stays pending_payment.
succeeded · failed · cancelled · expired—Terminal. A later event claiming otherwise is recorded and ignored.
Enforced twice, and the second one is the real one

Every mutation is a guarded UPDATE naming the state it expects — where id = … and status = 'pending_payment'. A row count of zero is the rejection. So a caller that skipped the table in TypeScript still cannot write an impossible history, and two confirmations racing each other produce one winner and one no-op rather than two sets of effects.

One divergence that is deliberate

A payment can succeed while its order refuses to move — the checkout expired while the buyer was on the provider's page. The payment transitions, because it did: money may genuinely have left an account. The order stays expired and no entitlement is granted. That divergence is a real operational event and it is visible precisely because the two are separate rows with separate states. It is listed as an open risk in section 8, because nothing yet reconciles it.

3

The trust boundary: five checks before anything is believed

The browser is never believed. A buyer returning from a hosted checkout page with ?status=success in the URL has proved only that they can type a URL. What is believed is a signed event, and only after five checks in this order:

  1. The signature verifies over the RAW bytes

    The body is handed to the provider unparsed. Parsing first and verifying the parsed shape is how signature checks get bypassed — the signature covers the bytes, not our interpretation of them. A test signs a valid event, alters one digit of the amount, and requires the same signature to be refused.

  2. The provider's event id has not been seen

    Unique index on (provider, provider_event_id).

  3. The reference resolves to a payment we created

    Not to an order id, which a caller could guess. An event for an unknown charge is recorded as rejected and refused.

  4. The amount and currency match exactly

    Minor units compared as bigint, currency compared as a string. A near miss is a mismatch. 4 999 against a 5 000 order is refused, and so is 5 000 EUR against 5 000 XOF.

  5. The transition is legal from the state the payment is actually in

    Not from the state the event assumes.

The endpoint requires no session — and that is the point

A provider has no cookie. Authentication at this endpoint is the signature. A browser test proves the consequence directly: the signed-in buyer posts a perfectly formed success event from inside their own session, and it is refused, because a session is not a signature and this handler has never cared about cookies.

Every refusal answers the same 400 and never says which check failed. Someone probing with forged amounts learns nothing from the response; the reason goes to payment_events and the audit log, where only we can read it.

What the client is allowed to say

A checkout request carries a store slug, a product slug, a quantity and an idempotency key. There is no price, currency, total, seller or commission field — not "validated and ignored", but absent, so there is nothing for a future edit to start trusting.

A browser test sends priceMinor: "1", totalMinor: "1", currency: "EUR" and commissionBps: 0 anyway. The order comes back at 9 000 XOF.

Visibility is in the WHERE clause, not applied after the read: p.status = 'published' and s.status = 'published', the same condition the public product page uses. A buyer cannot check out something they could not have seen, and a draft product is not fetched-then-refused — it is not found.

Why one transaction, and why the event row is written last

Everything a confirmation changes happens in a single transaction: the guarded payment update, the guarded order update, the entitlement, the frozen fees, and finally the event record. The guard comes first because it is what makes the whole thing idempotent. The event row comes last because it then carries what actually happened rather than what we hoped would happen when we started.

Committing the status and repairing the rest afterwards was the first design, and it is wrong: a missing commission rule would leave a paid order with no record of what it charged, and the provider's retry would refuse to touch it because the event id had been seen. Rolling everything back leaves the provider a clean slate to retry into.

5

The provider port, and what the mock does not prove

Stated plainly

No iPayMoney integration was added. IPayMoneyProvider still throws on every method, and its documentation is still unavailable. Nothing here demonstrates iPayMoney compatibility. What it demonstrates is that our boundary — signature over raw bytes, reference lookup, amount equality, legal transition, idempotent application — exists and holds under adversarial input.

The order domain depends on the PaymentProvider interface that Phase 1 defined, never on the mock. initiatePayment and applyProviderEvent both take a provider as an argument; neither imports one. Replacing MockPaymentProvider with IPayMoneyPaymentProvider is a change at the composition root, not in the order domain.

Three changes to the mock, each with a reason

ChangeWhy
Charges are created pending, not succeededAnswering "succeeded" synchronously permits an order domain written as call the provider, believe the reply, and that shape does not survive contact with a hosted-redirect provider. The asynchronous default forces the verification boundary to exist and be exercised by every test. The synchronous mode remains and is tested.
Permitted under a production build only with ALLOW_MOCK_PAYMENTS=yesThe browser suite runs next start, which means NODE_ENV=production. Exempting the test suite would have left the guard untested exactly where it matters. This is the two-variable shape ConsoleSender already uses: PAYMENT_PROVIDER is the variable a deployment gets wrong, and getting it wrong still cannot select the mock.
References carry an instance nonceA per-process counter restarted at 1 and collided with rows a previous run had written, under the unique index Afrinext keeps on provider references. A real provider's reference identifies a charge for all time; the mock's now does too.

The outcome a mock charge reaches is decided by its reference, which is derived from the order — so a test chooses success or failure when it creates the product it is going to buy, the way a real provider's outcome is decided by the buyer's funds rather than by our code path.

Two were not caught at first, and that is the useful part

The duplicate-grant guard. Removing on conflict do nothing from the entitlement insert changed nothing, because no test could reach it twice — the guarded transition already prevents a second attempt. So I looked for the case that does reach it: a buyer may open two orders for the same product, since the ownership check reads entitlements and neither order has granted one yet. Confirming both is reachable, and both confirmations must succeed — the buyer really did pay twice, and refusing the second would leave a captured charge with no order to explain it. There is now one grant and two paid orders, which is the correct answer and one nothing was asserting.

The consent gate at checkout. A pending_consent account resolves to no actor, so the gate is unreachable in the running system and removing it broke nothing. "Unreachable today" is a property of resolveActor, and a checkout relying on it would be one refactor away from selling to an unconsented account. The test now constructs the actor directly to reach the gate anyway.

The last row is the one I would draw your attention to: adding a ledger posting on confirmation is caught, so the boundary in section 1 is enforced by a test rather than by my intention to remember it.

Both in payments.test.ts, both reported here rather than buried

"captures a charge and reports it" asserted createCharge returns succeeded. The mock is now asynchronous by default, so it asserts pending — and a new test covers the synchronous mode, so the old behaviour is still exercised rather than dropped.

"never hands out the mock in production" matched the old refusal message. It now matches the new one, still asserts both the registry and the constructor refuse, and additionally asserts that ALLOW_MOCK_PAYMENTS must be exactly "yes". Strictly more coverage than before.

Open risks

ItemState
A payment can succeed against an order that has expired. The payment moves, the order does not, and nothing grants access — correct, but it means a buyer may have been charged for nothing. Nothing reconciles or refunds it yet, because refunds are not in scope. This is the highest-value thing to build next.needs work
Nothing sweeps expired checkouts on a schedule. expireLapsedOrders() exists and is tested; no job calls it. An order past its expiry is still refused at initiation, so the effect is stale rows rather than a wrong outcome.unscheduled
Digital delivery does not exist. An entitlement is a row saying someone owns a product; there is no file, no download, no course access. The library screen links back to the product page.next milestone
The commission rule must exist or a confirmation rolls back. Freezing the economics is inside the confirming transaction, so a missing rule for a product kind means the webhook 500s and the provider retries. That is the safe failure — but it is an outage until an operator adds the rule, and no alert fires.watch
The mock keeps charges in memory, so a server restart forgets them and a later event for an older charge is refused as unknown. Harmless for a mock; noted because it would be a data-loss bug in a real adapter.accepted
No refund path, no dispute path, no partial payment, no multi-item basket (the schema carries quantity and a line table, so a basket is a shape change rather than a new table).out of scope

One thing found on the way

.env.example no longer sets NODE_ENV

Setting it there overrides every command that knows better: next dev, next build, next start and vitest each set the right value for themselves. With NODE_ENV=development exported from the file, pnpm build failed while prerendering the global error page — and it is the same root cause as last milestone's CI failure, where the browser suite served a development build while CI served a production one. One line removed; both symptoms gone.

Proposed next, in the order I would take them: digital delivery for a paid entitlement, then the reconciliation and refund path for the expired-order case above, then settlement — which is the first thing that should touch the ledger, and the first that needs a real provider. Not started.
