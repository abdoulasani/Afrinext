Where the gate went, and why it cannot weaken authentication

You asked for this explained before anything else, so it comes first.

The enforcement point already existed

resolveActor has always returned no actor for any user whose status is not active — that is how suspension works, and it predates this milestone by two phases. So the entire gate is one word in the provisioning hook: a new account is created as pending_consent instead of active.

Created, then activated

One thing has to be said plainly, because it shapes everything else: consent records reference users.id. A consent cannot be recorded before the account row exists. Any design claiming to collect consent strictly before account creation is either storing it somewhere else — a parallel system, which you forbade — or describing itself inaccurately.

So the account is created and is not usable. Your own wording allowed for this: "created/activated". What a pending_consent account can do is nothing:

Why the acceptance endpoint does not require an actor

It deliberately does not call requireActor. A pending account has no actor by design — that is the gate — so an endpoint demanding one would be unreachable by exactly the people who need it. It resolves identity from the session instead: a weaker thing, and all this action needs. It grants no capability and can touch no account but the one the session belongs to.

Activation is one transaction, or nothing

await db.transaction(async (tx) => {
  accepted = await acceptCurrentVersions(tx, userId, ACCOUNT_CONSENT_KINDS, options, context);
  // Belt and braces: re-ask the gate rather than trusting the loop above.
  await requireConsent(tx, userId, ACCOUNT_CONSENT_KINDS, options);
  // Conditional: accepting terms cannot revive a SUSPENDED account.
  update users set status = 'active' where id = … and status = 'pending_consent'
});

Recording without activating locks someone out of an account they agreed to. Activating without recording is the failure this milestone exists to prevent. Neither is a state that can exist.

CI went red, and the reason was not this change

Read this section first

The first commit of this milestone, ccb2700, passed everything locally and failed in CI: four browser tests, all at the moment a verification code is requested. The milestone's own change was not involved. What the failure exposed was two defects that had been sitting in the repository since Phase 1 — one of them a control the senior review had explicitly asked for and that was not actually running in the application.

Both are fixed in e3ded66. Neither would have been found by any test that existed, and neither could have been found locally, for the reason immediately below.

Why local was green and CI was red

next start sets NODE_ENV=production only when it is not already set — and .env sets it to development for the dev server. So every local browser run served the application in development mode while CI served it in production mode. Two behaviours differ across that line, and both matter here:

  • Better Auth enables its own rate limiter only under NODE_ENV=production. Locally it was off. In CI it was on.
  • The session cookie is marked Secure only in production — so the suite was not exercising the cookie behaviour its own configuration file claimed it was.

The browser suite now pins NODE_ENV=production in the server command. That is the whole fix for the divergence, and it is load-bearing: with the old limiter restored and the pin removed, the same build passes locally; with the pin in place it fails, in exactly the way CI failed.

Defect one — a literal that overrode the reviewed policy

The phone-OTP plugin declared a Better Auth rate rule of ten requests a minute on /phone-otp. The suite makes fourteen sends from one address, so in CI the eleventh was refused and the remaining tests failed on a 429 that had nothing to do with what they were testing.

The real problem was not the number

It was that a literal in code silently overrode stored configuration. An operator who raised perIpPerHour to 200 in platform_settings would still have been capped at ten a minute by a number nobody could see, from a limiter that keeps its counters in one process's memory and answers in its own shape — no audit row, and not the ratelimit.exceeded contract the rest of the API uses.

The backstop is now derived from the same policy and deliberately set above it — twice the hourly allowance, inside one minute. High enough that the refusal a caller actually meets is always the audited PostgreSQL one; low enough that a flood from a single address is still stopped before it reaches the database. /phone-otp/verify keeps a tight rule of its own: attempt counts are bounded per challenge by PostgreSQL, but nothing else bounds how fast one address may hammer that endpoint.

Defect two — decision 7 was satisfied in the package and not in production

Chasing the first defect turned up the second. loadOtpPolicy() was written, tested and correct. Nothing called it. apps/web built the auth instance without a policy, so every request used the compiled-in defaults and an operator's UPDATE to platform_settings changed nothing at all.

How a passing test suite missed it

The domain tests called loadOtpPolicy themselves and asserted it returned the stored row — which it did. The one call that was missing was the one nobody tested: the application's. A test that performs the integration it is meant to be checking will pass on any build, wired or not.

The policy is now a resolver, consulted on the request that issues a code rather than once at construction. That distinction is not decoration: the auth instance is built once and cached for the life of the process, so a value resolved at construction would pin whatever the table held at boot and turn "change a limit" back into "deploy". The code's lifetime and attempt bound come from the same read, so ttlMs and verificationAttempts are configuration now too.

Five tests cover the wiring. Three are domain tests; two are browser tests that change a row in platform_settings and then ask the real server, over HTTP, for real codes — deliberately end to end, because the defect lived precisely in the gap a unit test cannot see. One of them raises a limit and requires the running process to follow it without a restart.

Nothing about the OTP guarantees moved

Codes are still stored only as a keyed HMAC in otp_challenges.code_hash; the plaintext path is still absent and still asserted absent; single use, the attempt counter and one-live-challenge are still enforced by PostgreSQL; every verification failure still answers identically. The reviewed limits themselves — 5 per phone per hour, 20 per IP per hour, 60 s cooldown, 5 attempts, 5 min lifetime — are unchanged. What changed is that the application now reads them.

The browser environment still raises only the per-IP ceiling in platform_settings, the same UPDATE an operator would run — and as of this commit that UPDATE actually does something.

What the last two rows are for

The third is the diagnosis, executed rather than argued: restoring the literal produces the same five failures, in the same specs, at the same point in the run, and stretches the run to the same 1.4 minutes CI took. The fourth then removes the NODE_ENV pin and the identical broken build passes — which is the local-green / CI-red divergence, demonstrated rather than asserted.

The first row also found a weak assertion of my own. One new test sent a code and expected the next send to be refused; under the mutation it was refused anyway, by the cooldown rather than the limit, so it passed while proving nothing. It now requires the second send to succeed — which only a build that reads the stored one-millisecond cooldown can do — before requiring the third to be refused.

Two things I want on the record

Three mutations first reported as "not caught" had never actually applied. The edits failed silently against a shell-quoting problem and the suite passed because the code was unchanged. Every mutation above now asserts that the file changed before its result is believed. A mutation that does not apply proves nothing, and reads exactly like a test gap.

The fourth is genuinely uncaught, and I have left it in. The re-check inside the transaction is redundant with the acceptance loop directly above it, so by construction no test can distinguish its presence. It stays as defence against a future change to the acceptance path that silently records less than it should — but nothing proves it works, and this packet is the record of that.

The third row is the one I would settle next, and it is a one-line decision: leave existing accounts alone, or mark them pending_consent so they are prompted on next use. There are no production accounts yet, so the cost is zero today and rises from here.

The decision I actually need from you

Better Auth's in-memory limiter and our PostgreSQL one both guard the same endpoint. I have made the first strictly looser than the second, so it bounds a flood without ever pre-empting the configured policy, and so the refusal a caller meets is the audited one. The alternative readings are tighter (accept that a burst is refused unaudited, in a shape that does not match the rest of the API) or removed entirely (rely on PostgreSQL alone, which is authoritative and multi-instance but does one round trip per refused request). I chose the middle. It is a rate-limiting parameter on an unauthenticated endpoint, so I would rather you agreed than assumed.
