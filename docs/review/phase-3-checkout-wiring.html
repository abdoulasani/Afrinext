Afrinext · phase 3 · checkout → iPayMoney wiring

Three Fields Arrive, One Does Not Exist

The blocker the last report closed on is fixed as far as Afrinext's own data allows. The payer's number and country now reach the provider from the buyer's own account. A real iPayMoney charge still refuses — and it now refuses naming customer_name, which is a field no part of Afrinext has ever collected.

Branch claude/create-app-repository-1cxsih HEAD 49c043f Unit tests 491 passed Browser tests 31 passed Mutations killed 24 / 26 Real sandbox calls 0
The one-paragraph answer

iPayMoney requires four things Afrinext was not sending. Three now arrive: the payer's verified phone, the buyer's country when we hold one, and the payment channel when the caller chose one. The fourth — customer_name — cannot be sent, because Afrinext has never asked a buyer for a name. What sits in the name columns are placeholders written at signup to satisfy a NOT NULL: a synthetic address and the phone string.

Sending either would be inventing a value for a provider-required field, so the adapter still refuses. That refusal is the correct outcome and the honest end of this milestone. Closing the gap is a product decision — decision 1 in section L.

The data path, buyer to provider

buyer signs in (phone OTP)
  └─ Better Auth  user.phoneNumber          verified by the OTP
     user.name = the phone string           placeholder, NOT NULL
  └─ users.auth_user_id  ──────────────────  the link
     users.display_name = 22790…@phone.afrinext.local   placeholder
     users.country_code = NULL              no signup path writes it

checkout            createCheckout()        prices the order server-side
  └─ order row      total_minor, currency

pay                 payOrderAction()        posts orderId only
  └─ initiatePayment()
       ├─ reads the ORDER for the amount            unchanged
       ├─ reads the BUYER for their details         NEW
       │    select u.country_code, a."phoneNumber"
       │      from users u
       │      left join "user" a on a.id = u.auth_user_id
       │     where u.id = actor.userId
       ├─ writes the payment row  (initiated)       before the call
       └─ provider.createCharge({
              customer: { userId, phone },
              channel,
              metadata: { country, buyerCountry },
          })

Every field is read server-side from the buyer's own account. None is accepted from the caller, and that is the same rule the amount already follows: a field a caller can set is a field a caller can change. A buyer must not be able to tell the provider that somebody else's number is paying.

The phone comes from Better Auth's table because that is where sign-in verified it. Using the verified number matters — it is the one that answered an OTP, not one typed into a form.

Why no name is sent

Two columns look like they hold a name and neither does:

ColumnWhat it actually holds
users.display_name22790123456@phone.afrinext.local — the synthetic address signup mints so Better Auth's NOT NULL email is satisfied
user.nameThe phone string itself, written for the same reason

Passing either would be inventing a value for a provider-required field, which this milestone is explicitly not allowed to do. The second would additionally hand a payment provider an internal hostname. A test asserts that nothing matching phone.afrinext.local ever appears in the metadata.

There is also nowhere a buyer could supply a name: the application has no profile or account-settings screen at all.

Why the country travels twice

iPayMoney documents country only as « le code du pays de la transaction » and does not say whose country that is. That is question K17, and it is unanswered.

The order layer must send something or send nothing, and it holds two countries: the buyer's and the store's. It sends the buyer's, because the buyer is the payer — and it sends the same value a second time under buyerCountry, which states unambiguously what the value is.

This does not answer K17. When iPayMoney answers, the fix is to change which of our facts fills country; nobody has to reconstruct what the value once meant. The choice is recorded as assumption A11.

A test makes the buyer Nigerien and the seller Ivorian, so "the buyer's country was passed" is a real assertion rather than a coincidence of both being NE.

A defect this milestone had to fix to make "refused safely" true

Before this change, a throw from createCharge left the payment row at initiated forever. payments_one_live_per_order means initiatePayment returns any live row instead of calling the provider — so every later attempt on that order returned the stuck row and did nothing. The buyer would have clicked pay forever.

It never showed under the mock, which does not throw. It would have shown on the first real iPayMoney charge. A refusal now closes the payment and the order, so the buyer gets a clear failure and can start a fresh checkout — the same outcome the existing "provider refuses at initiation" path already produced.

E

A throw is not a failed charge

Closing the payment on a refusal is safe only because the refusal is classified, not assumed. This is the approved Phase 3 correction applied one layer up: unknown must never become failed.

What was thrownTreated asPayment
ProviderNotConfiguredError — the adapter declined to build a request, or the provider answered a documented refusal stating no payment was createdno charge existsfailed, order closed
Transport failure at stage not_transmitted — DNS, connection refused, unreachable hostno charge existsfailed, order closed
Timeout, connection reset, HTTP 5xx, unparseable answerunknownleft initiated, order left pending_payment

A 5xx arrives after the request reached iPayMoney, so the charge may exist under our idempotency key. Marking it failed would assert that no money moved, which nobody can support. A test drives a real 502 through the adapter and asserts the payment stays initiated and the order stays open.

The adapter owns the classification of what its own errors mean; this layer honours it rather than re-deciding from an HTTP status. That is the same division the refund path already uses.

H

Provider assumptions made

One, recorded as A11 in the assumptions register rather than left in code.

A11

Afrinext's checkout provisionally sends the buyer's country in country. The order layer holds two countries and must choose or send nothing; the buyer is the payer, so the buyer's country is sent.

It is provisional and it does not answer K17. The same value travels as buyerCountry, which names what it actually is, so answering K17 changes which fact fills country rather than requiring anyone to work out what was meant.

No other assumption was made. In particular: no default channel was chosen, no name was synthesised, no country was inferred from a phone prefix or from the store, and no provider behaviour was invented. Nothing was added to support-questions.md — the code raised no new question that K1–K18 did not already cover.

L

Decisions needed from you

  1. Where does a buyer's name come from?

    This is the last field, and it is a product question rather than a wiring one. Three routes, and I am not taking any of them without you:

    • Ask at checkout. One field on the payment step, stored on the order or the account. Touches no authentication and is the smallest change — but it adds friction exactly where a buyer is about to pay.
    • Ask once, after signup. A profile step that fills users.display_name with a real name. Better data, and it needs a screen the application does not have.
    • Ask at signup. Best data, and it changes the OTP flow — which I will not touch without explicit approval.

    The same screen could collect the buyer's country, which would close S8 and make country reliably present at the same time.

  2. Should checkout offer a payment channel?

    iPayMoney documents mobile and card with no default, so the adapter refuses without one and nothing defaults it. Today no screen asks. The smallest change is a two-option control on the payment step; whether Afrinext offers cards at launch at all is your call, not an implementation detail.

  3. Sandbox credentials.

    Unchanged from the last report and still the thing that turns hypotheses into facts. Sixteen tests are written and waiting.

Nothing here needs retroactive approval

No approved state machine or business rule was changed. The one assumption made is A11, and it is provisional, documented, and reversible in one line. Settlement was not touched, nothing is merged to main, no sandbox readiness is claimed, and no provider behaviour was invented.
