The Refund That iPayMoney Does Not Document

The official documentation is now in the repository. It defines two payment endpoints, a webhook, and a sandbox. It defines no customer refund of any kind — and the word that looks like one means something else entirely.

Code state 3fe233d CI green Unit tests 429 Browser tests 31 Refund questions answered 15 / 15 Documented refund operations 0
The single most important finding

The documentation uses « remboursement » — the ordinary French word for a refund — for an operation that is not a refund:

« Vous pouvez à tout moment demander depuis votre tableau de bord le remboursement de vos avoirs. Cela s'appelle un reversement. » — extract L97

Your holdings, to your account. That is the merchant withdrawing their own balance to their own mobile-money or bank account, with a 50 000 FCFA floor and a three-day holding rule. Every one of the 30 occurrences of remboursement and reversement in the document carries that sense. There is no other.

Reading it as a customer refund would have produced an integration that pays the merchant when a buyer is owed money. That is the trap this gate was called to check, and it is a real one.

Two contract mismatches found — reported, not fixed

1. ChargeStatus.amount is required and iPayMoney never sends an amount. Neither the webhook payload nor the payment-status response carries one. A faithful getCharge() cannot be written: the adapter would have to fill the amount in from our own database, which is us telling ourselves what we already believe rather than the provider corroborating it.

2. VerifiedEvent.providerEventId has no counterpart. Our replay defence is UNIQUE (provider, provider_event_id). iPayMoney sends no event id and retries five times on non-2xx, so duplicate deliveries are certain rather than hypothetical. The adapter would have to derive an id from the fields the event does carry.

Neither is a defect in the Phase 3 refund implementation, and neither has been changed. They are properties of the charge contract that the new documentation exposes, and they belong to the iPayMoney integration milestone. Deriving an event id is sound — a repeat of the same (reference, status) fact is exactly what deduplication should collapse — but it is a decision to take deliberately, not silently.

One thing this gate deliberately did not tidy

The header comment in packages/core/src/payments/ipaymoney.ts still says the documentation "is not available in this repository". That sentence is now false. It is a comment, not behaviour, and correcting it means touching an implementation file during a gate that was told not to. A design decision this documentation validates

The POST returns "status": "succeeded" synchronously, and iPayMoney also sends a webhook for the same fact. Phase 2 deliberately clamps a provider's synchronous answer to pending and confirms nothing until a verified event arrives. That was written against a mock, on the argument that a synchronous answer travels on a connection the caller may control. The real provider turns out to behave exactly the way that argument assumed — the boundary was built for the right shape.

The signature, and why it is a finding

The prose and the example disagree, and both readings are worse than what our boundary is built to verify.

SourceSays
Prose (L332)"Il est introduit dans l'en-tête de chaque requête x-iPayMoney-secret une signature"
Example (L338)"secret-hash": "sk_58951rhguiq859905dfn5903gh"
Setup instructions"Remplissez votre Secret Hash. C'est votre clé API secrète" — copy it from the API Keys page
What this appears to mean, and why it must be asked

The header name differs between prose and example. More seriously, the example's value is the secret key itself (sk_…), and the setup text says the Secret Hash is the API secret. If that is what it means, then this is a static shared secret echoed in a header — not a signature over the request body.

Two consequences follow, and neither is theoretical:

  • The check does not cover the payload. Anyone holding the secret can forge any event body. A signature over the raw bytes cannot be forged without also producing a matching digest; a constant header can.
  • The secret is transmitted on every single webhook, to our endpoint, five times over on retry — so it appears in any proxy log, any error report, any request dump.

Afrinext's webhook boundary verifies a signature over the raw bytes before parsing, and that property is load-bearing: it is why a forged amount cannot confirm a payment. Combined with finding F1 — no amount anywhere — a forged event would face no amount check either. This is question K1, and it should be asked before any webhook is trusted with money.

What this means operationally — and whether the design still holds

You asked specifically whether the existing Phase 3 design safely handles unknown refund capabilities. It does, and the reason is structural rather than lucky.

Design decisionMade when refunds were an unknownAgainst the real documentation
getRefund() is optional on the interface, and callers branch on supportsRefundQuery()To avoid asserting a capability we could not confirmcorrect — there is no refund query, so the false branch is the real one
An in_doubt refund is never retried, only resolvedBecause a timeout is not evidencecorrect — and now load-bearing, because no mechanical resolution exists at all
Manual reconciliation exists as a first-class path, with dual control and an external referenceAs the fallback for a provider that cannot be askedcorrect — it is not the fallback. It is the only path.
The refund's provider, amount and currency are frozen by a triggerTo keep a snapshot honestcorrect — and more valuable now, since the provider corroborates no amount anywhere
Refunds post nothing to the ledgerBecause Phase 2 posts no capturecorrect — and now also avoids booking a reversal for an operation that has no provider mechanism
refund() and getRefund() on the iPayMoney adapter throwBecause nothing was knowncorrect — and must keep throwing, because nothing is known still
The operational consequence, stated plainly

The Phase 3 design named a scenario as its worst case: "if both R3 and R4 are no, every timed-out refund becomes a human reading a statement."

The documentation is worse than that scenario. It is not that ambiguous refunds need a person — it is that every refund needs a person, from the very first one, because there is no API to attempt one through. Afrinext currently has no automated way to return money to a buyer through iPayMoney.

The machinery built in Phase 3 is not wasted by this — the debt is still recorded automatically and inside the confirming transaction, the queue is still age-sorted, the evidence requirements and dual control still apply, and reconciliation still reports a debt nobody paid. What changes is which path carries the volume: manual reconciliation is not the exception, it is the process.

#BlockerWhy Settlement cannot proceed past it

S3The amount is not verifiable from the provider — F1The ledger's first commandment is that the books are the truth. Booking a capture against an amount no provider will confirm makes the ledger authoritative about a number only we assert

Recommended next milestone

Not Settlement

Settlement is blocked by six things (§J), four of which only iPayMoney can answer. Starting it now would mean writing ledger postings against assumptions about settlement timing, fee treatment and amount verification that the documentation does not support.

Recommended: send the questions, then integrate payments against the sandbox

In that order, and the first step costs nothing but an email.

  1. Send K1–K16 to support@i-pay.money

    K1 and K5 first. Until they are answered, no amount of code changes the fact that there is no documented way to refund a buyer. This is not a development task and it should not wait for one.

  2. iPayMoney payment integration, sandbox only

    Implement createCharge, getCharge and verifyWebhook against the two documented endpoints, and drive all five sandbox scenarios — especially the 180-second pending, which exercises the late-payment grace window against a real provider instead of a mock. refund() and getRefund() keep throwing, because nothing has changed about them.

    Two contract questions must be decided deliberately in that milestone, not silently: how a providerEventId is derived when the provider sends none, and what getCharge() does about an amount the provider will not state. Both are in §B.

  3. Start the Live activation submission in parallel

    It is a queue with an unknown wait, not a task. Beginning it during the sandbox milestone costs nothing and may save weeks.

  4. Then Settlement

    With T+N confirmed, fee treatment confirmed, and at least one real payment observed end to end.
