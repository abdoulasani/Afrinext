The correction you required, and where it lives

The approved design classified an HTTP 5xx as a definite failure. You corrected that before implementation, and the corrected rule is now the axis the whole phase turns on: an HTTP status never decides whether the financial operation happened. The classifier asks only how far the request got. A 5xx received after transmission is in_doubt, and in_doubt is never retried.

It is enforced in one place — payments/refund-outcome.ts — proven by six adversarial tests and by mutations R1, R2 and R3, each of which makes a test fail. Section 10 shows the output.

Migration 0012, and what the database refuses on its own

The point of this section is that most of the safety is not in application code. Twelve CHECK constraints, five unique indexes and one trigger enforce it, so a future code path — or a direct UPDATE — fails loudly rather than quietly.

The provider boundary — where the correction is enforced

One file decides failed versus in_doubt, and it never reads an HTTP status to do it. Three stages, and only the first can produce a plain failure:

StageMeansBecomes
not_transmittedWe can prove the request never reached the providerfailed retryable
transmittedThe bytes left. What the provider did with them is a separate questionin_doubt unless the answer carries evidence
unknownWe cannot establish whether they leftin_doubt

The not-transmitted set is short, closed, and asserted

On the listWhy it is proof
ENOTFOUND · EAI_AGAINDNS never resolved a host to connect to
ECONNREFUSED · EHOSTUNREACH · ENETUNREACH · EADDRNOTAVAILThe transport refused, or could not reach the host
TLS handshake failures (5 codes)Failed before any application bytes
ERR_INVALID_URLWe never built a request
Deliberately absentWhy it is not proof
ECONNRESETThe peer reset — which can happen after the request was fully sent, and even after it was processed
ETIMEDOUTA timeout says only that no answer came back
EPIPEThe socket closed mid-write; some bytes may have gone
ABORT_ERRWe gave up. The provider did not necessarily
UND_ERR_*undici's own timeouts, all post-connection
every HTTP statusA response existing at all proves the request arrived. A 500 says the provider's web tier had a problem, and nothing about the refund it may already have accepted

There is no beneficiary field, no account field and no destination field on the interface, so no API request, server action or test is in a position to redirect a refund. The money goes back the way it came because that is the only thing the interface can express.

Idempotency — four layers, none of which trusts the others

#LayerCovers the case the others do not
1UNIQUE (payment_id)Whatever races and whatever crashes, a second refunds row for one payment cannot exist. Not a read-then-write — the index is the guarantee
2SELECT … FOR UPDATETwo operators pressing at the same instant serialise instead of both reading owed
3Guarded transitionEvery UPDATE names the state it expects, so a caller that got past the lock with a stale read matches no rows and changes nothing
4Attempt row committed BEFORE the callA crash between the commit and the response leaves an open attempt — evidence a request may be out there, rather than silence

On top of all four, the absolute rule: in_doubt is never re-sent, only resolved.

The derived key

/** Derived, never supplied. A caller has no say in what the provider is told. */
export function refundIdempotencyKey(refundId: string, attemptNo: number): string {
  return `refund:${refundId}:${attemptNo}`;
}

No route, action or test supplies a key. Two attempts on one refund get distinct keys — which is correct, because a retry only happens after the previous attempt was proven not to have reached the provider, and reusing a key there would make a provider that cached the failure return it forever.

Concurrency — against a lock actually held on a second connection

Why not Promise.all

Promise.all cannot reliably interleave two database transactions, so a test built on it passes whether or not the lock exists. This test holds the row: a separate pooled connection takes for update, an execution arrives and must block, the holder changes the refund underneath it and commits, and only then does the waiter get to look. What it must find is the state the holder left — and refuse to act on the state it read before waiting.

The crash window — observed from inside the provider call

The claim is an ordering: the attempt row is committed before the provider is called. A test that asserted this after the fact would prove nothing, so the test observes it from inside the call, on a separate connection, at the exact instant a crash would occur.

const crashing = new MockPaymentProvider();
Object.assign(crashing, {
  refund: async () => {
    // A SEPARATE connection: only committed data is visible here, which is
    // exactly what would survive if the process died on the next line.
    const client = await getPool().connect();
    attemptsVisibleDuringCall = (await client.query(
      "select count(*)::int as n from refund_attempts where refund_id = $1", [refundId])).rows[0].n;
    refundStatusDuringCall = (await client.query(
      "select status from refunds where id = $1", [refundId])).rows[0].status;
    client.release();
    throw new RefundTransportError("process died here", "unknown");
  },
});

await executeRefund(db, finance, crashing, refundId);

expect(attemptsVisibleDuringCall).toBe(1);        // durable before the call
expect(refundStatusDuringCall).toBe("in_flight");

Why the sweep lands where it does

Sweeping to in_doubt says "we stopped waiting", not "it failed". It unlocks nothing and permits no retry — it only removes the claim that a response is still coming. A sweep to failed would turn every crashed process into a duplicate refund, which is what mutation R15 demonstrates.

The CI gate proves the detector, not just the data

Ten checks over a table that is empty on most CI runs would report "clean" and mean nothing. So the gate builds a consistent refund, requires silence, breaks the frozen amount, requires the detector to speak, and rolls the whole thing back. Actual output:

Ledger reconciliation clean over a real capture → settlement → payout cycle.

The counts read zero because the probes run inside a transaction that is always rolled back. They plant rows that are deliberately wrong, so they must leave nothing behind — and deleting afterwards turned out to be the wrong instrument: the refund probe could not delete its own refund, correctly, because a refund is resolved and never erased. A cleanup that has to disable a trigger is a cleanup that could disable the wrong one. A rollback removes everything without asking any table's permission, and removes it even if the probe throws halfway.

Each probe also asserts silence about its own rows rather than about the whole database. Asserting a globally empty report made the probe a hostage to whatever the suite left behind — one unrelated anomaly and a working detector would report that it cannot detect, which is the opposite of the truth.

The gate exits non-zero if either probe stops behaving — a reconciliation that cannot report a fault is not a gate. Mutations R22, R23 and R24 each break one detector and are each caught.

A bug the harness itself found

An early mutation run was killed by a timeout before it could restore the source, and the next run then captured the mutated file as its own backup and restored that — quietly making a mutation into the code. Two mutations survived that way for several minutes and were caught because a test that had been passing started failing consistently. Manual reconciliation — dual control that adapts without becoming a fiction

This is the only place a human's word becomes financial truth, so it is the most dangerous operation in the phase. Four things stand between an operator and a fabricated success:

  1. An external reference is required for a success

    Claiming money went back means naming what the provider calls the refund — a claim somebody else can check against the provider's own records later. The route refuses without it, and so does a CHECK constraint.

  2. Step-up elevation

    Holding refund.reconcile_manual says allowed in principle. Elevation says present right now.

  3. Two people, where the deployment has two people

    One proposes what a statement says; a different one confirms. Proposing changes nothing about the refund. Neither half moves money alone.

  4. A distinct resolution source

    resolved_by = 'manual_reconciliation' is its own value, so every refund resolved this way can be listed, counted and re-audited by somebody who was not involved.

Your decision 4, implemented as stated

You asked for B — two-person where operationally possible — with A as a temporary fallback, and said explicitly: do not invent a second-user requirement that cannot actually be enforced.

So the requirement counts the actual holders in SQL at the moment of confirmation:

const eligible   = await countManualReconcilers(db);   // distinct live global holders
const samePerson = proposer === actor.userId;

if (samePerson && eligible > 1) {
  throw new ManualReconciliationError("refund.second_person_required",
    "Another person who can reconcile refunds must confirm this. You proposed it, "
    + "so you may not also confirm it.");
}
const mode = samePerson ? "single_operator" : "two_person";
DeploymentBehaviourRecorded as
Two or more holdersThe proposer cannot confirm. No flag, no override, no force parametertwo_person
Exactly one holder — Afrinext todayThe same person may confirm, with elevation and the full evidence trailsingle_operator

A single_operator resolution is not silently identical to dual control. It is a distinct stored value, and a reconciliation detector reports it by name on every run — so the weakest control in the system is countable rather than invisible.

The adaptation is not a hole an operator can open

A finance user cannot revoke the second holder to gain self-confirmation: changing role assignments needs admin.role.grant, which the finance role deliberately does not hold. The separation of duty that already existed for withdrawals is what makes this rule enforceable.

The notification outbox — a queue with no sender, on purpose

Your decision 6 was to add the outbox now and connect no SMS provider. That is exactly what exists.

PropertyHow
Written in the same transaction as the fact it announcesA send inside the transaction blocks it on a third party; a send after it is a message lost to a crash. A row commits with the fact — either both happened or neither did
One message per event per subjectUNIQUE (kind, subject_type, subject_id) with on conflict do nothing. A retried resolution tells the buyer once
Facts, never a rendered messageThe payload holds the outcome and the ids. Translation and formatting belong to whichever sender is eventually chosen, which knows the recipient's locale
Nothing can claim deliveryThere is deliberately no markSent function. A function that moved rows to sent with no provider behind it would put a lie in the database, and "the buyer was notified" is exactly the lie that surfaces during a dispute

Four kinds are queued: refund.owed when the debt is recorded — deliberately at the moment the buyer starts wondering where their money went, not when it arrives — and refund.succeeded, refund.failed, refund.in_doubt on resolution.

The browser test asserts one refund.succeeded row for the subject and zero rows in any status other than pending. No SMS provider has been chosen for Niger and none was invented.

iPayMoney — the blockers, and the two that change the design

Stated plainly

No iPayMoney integration exists and none was attempted. Nothing about their refund endpoint, payloads, error codes or signature scheme has been invented anywhere in the codebase. refund() throws. getRefund() is declared and throws. The adapter is non-operational and will remain so until the official contract and sandbox credentials are verified.

Ten refund facts are now documented in docs/providers/ipaymoney/README.md. Two are design-changing rather than parametric:

#RequiredWhy it changes the design
R3Does a refund status query exist, and what can it be queried by?The only mechanical way an unknown is ever resolved. Without it, every ambiguous refund waits for a person
R4Do refunds accept a caller idempotency key, and can a refund be looked up by that key afterwards?After a timeout we hold no provider refund reference — our key is the only handle. Without lookup-by-key, R3 cannot resolve the exact case that most needs resolving
R2Which error codes mean, in their own words, "no refund was created"Not design-changing, but expensive if absent: with no documented list, every provider rejection becomes a manual reconciliation instead of a safe retry
R1 · R5–R10Endpoint and enumeration; refund webhooks and their signature; whether the webhook names the charge; time limits; partial support; post-acceptance failure; sandbox controls for rejection, timeout and duplicateParametric — they fill in an adapter that already has a shape
The answer that costs money is "no" to both R3 and R4

If iPayMoney can neither be asked about a refund nor be asked about our own key, then every refund whose request does not come back becomes a human reading an iPayMoney statement and reconciling it under dual control. That path exists and works — it is not a gap. But it is a staffing cost that scales with transaction volume, and whoever staffs finance should learn it before launch rather than on the first timeout.

Why getRefund is declared-and-throwing while createPayout is absent: omitting a method asserts the provider may lack the capability, and supportsRefundQuery() returning false makes callers treat every ambiguity as manual by design. Declaring it keeps the adapter non-operational without deciding R3 on iPayMoney's behalf.
