No customer-refund API was invented, anywhere. There is no endpoint, method, request body, response shape, status value, webhook, sandbox scenario, fee or processing time for one in the documentation, so there is none in the code. The word « remboursement » appears throughout the document and means reversement every time — the merchant withdrawing their own holdings, with a 50 000 FCFA floor and a three-day rule. Building a customer refund on it would return the merchant's money to the merchant while a buyer waits.

getRefund() is declared and throws, while createPayout() is simply absent, and the asymmetry is deliberate. Callers branch on supportsRefundQuery(provider), which reads whether the method exists. Omitting it would assert on iPayMoney's behalf that they have no refund-query capability, and that assertion makes every ambiguous refund a manual reconciliation by design. That is the operational reality today, but it should be true because iPayMoney said so — question K2 — not because this file decided it.

C

The three decisions this milestone had to make

Each one is a place the documentation stops and the code cannot. Each is recorded here with what was chosen, what it costs, and what would change it.

1 · ChargeStatus.amount — made optional, and iPayMoney states none

Afrinext's webhook boundary cross-checks the confirmed amount against the order's amount. iPayMoney supplies no amount in either channel: not in the webhook payload, and not in the payment-status response.

Three options existed. Two were refused:

OptionVerdictWhy
Copy our own order amount into the ChargeStatusrefusedThis is the failure the milestone brief named explicitly. The cross-check would then compare the order's amount against the order's amount and pass every time — a check that cannot fail is worse than no check, because it reads like one
Keep amount required and send a zero or a placeholderrefusedA zero is a number. Downstream code cannot tell "the provider said nothing" from "the provider said nothing was charged"
Make amount optional and declare the capabilitychosenAbsence is representable, and statesChargeAmount makes it a fact a caller can branch on and a test can assert
 
// provider.ts
readonly amount?: Money | undefined;   // ABSENT when the provider states none

// PaymentProvider
readonly statesChargeAmount: boolean;  // mock: true · ipaymoney: false

The cost, stated plainly: for iPayMoney the amount cross-check cannot run. The charged amount is not independently verifiable from the provider at all. That is question K8, and it is a Settlement blocker (S3) rather than something the adapter can solve.

The real-sandbox suite contains a test named CONFIRMS OR REFUTES that no amount is returned. If iPayMoney does return one, that test fails loudly and statesChargeAmount becomes true on evidence.

2 · Missing providerEventId — derived, not invented

Afrinext's replay defence is UNIQUE (provider, provider_event_id) on payment_events. iPayMoney sends no event id and retries five times on any non-2xx, so duplicates are not a hazard to guard against — they are the documented behaviour.

ipaymoneyEventId(reference, confirmedStatus) = `${reference}:${confirmedStatus}`
IngredientWhy it is in
referenceiPayMoney's own identifier for the payment, so two different payments cannot collide whatever else is equal
statusSo a success and a failure for the same payment do not collapse into one another. Keying on the reference alone would silently discard a later, truthful event as a duplicate of an earlier, different one
the confirmed statusNever the claimed one. A claimed value would let anyone reaching the endpoint mint fresh ids at will, and each fresh id is a row and a lookup
no body hashDeliberately absent. A retry that re-serialises the payload is the same fact; a byte-level id would differ between retries and defeat the deduplication it exists for. The id names the fact, not the delivery

Proved against a real database, not asserted about a string: ipaymoney-replay.test.ts delivers one event five times through applyProviderEvent and the real domain, and asserts one entitlement, one event row, and a clean commerce reconciliation.

If iPayMoney does send an id we have not seen — question K9 — theirs replaces ours and the derivation is deleted.

3 · The webhook signature — the ambiguity was isolated, then neutralised

The security finding

The documentation describes webhook authentication three incompatible ways: the prose names a header x-iPayMoney-secret containing "une signature" (L332); the example shows secret-hash whose value is the secret key itself, sk_... (L338); and the setup instructions say to paste the API secret into a dashboard field called "Secret Hash".

Read together, that is a shared secret echoed in a header — not a signature over the request body. It does not cover the payload. Anyone who obtains the secret from a log, a proxy or a mis-scoped error report can forge any event, and the secret is transmitted on every single webhook.

The brief said: if the documentation cannot establish the correct cryptographic verification algorithm, isolate the ambiguity and stop before implementing an unsafe verification scheme. The ambiguity was isolated and put to you as three options. You chose A.

OptionConsequence
A · Treat the notification as a trigger, then ask the providerchosenVerification depends on iPayMoney's API being reachable, and costs one extra request per notification
B · Implement the header check alone and trust it—A leaked secret becomes a forged payment
C · Leave verifyWebhook throwing until K7 is answered—No payment can ever be confirmed, and the answer may take weeks

As implemented, verifyWebhook:

  1. Checks the header in constant time

    Both documented names are accepted, because the documentation contradicts itself and guessing wrong would reject every real webhook. Accepting either is not a weakening — the value still has to match, and the value is the whole check. The comparison is timingSafeEqual, with the length compared first because it throws on a length mismatch and the length of a secret is not the secret.

  2. Reads exactly one field out of the body

    The payment reference, and nothing else. Not the status, not the msisdn, not the external reference.

  3. Asks iPayMoney directly

    GET /api/v1/payments/{reference} over our own authenticated outbound connection. The returned event carries the confirmed status; the claim never reaches the caller.

  4. Records what was claimed alongside what was confirmed

    raw.claimed is the notification's own words, screened for secrets and truncated. It is what makes a forgery attempt visible after the fact rather than invisible.

Forging a notification therefore buys nothing. It can make Afrinext ask a question; it cannot answer one. This holds even if the secret leaks — which the documented scheme, on its own, does not.

What it costs, stated plainly: verification now depends on iPayMoney's API being reachable. When the lookup fails, nothing is confirmed, the route answers non-2xx, and iPayMoney retries — the event is not lost, and an unconfirmable notification is never treated as a confirmation. It does not fix the amount: the status endpoint states none either.

Question K7 stays open. If iPayMoney confirms a real body signature, the lookup becomes an optimisation rather than the safety property, and the method simplifies on evidence.

E

Status mapping — two entries, and everything else refused

IPAYMONEY_STATUS_MAP = {
  succeeded: "succeeded",
  failed:    "failed",
}

Those are the only two status values that appear anywhere in the documentation (L183, L246, L364). Anything else throws IPayMoneyUnknownStatusError naming the exact string received.

A scenario is not a status

The sandbox names five scenarios — success, error, insufficient_fund, declined, pending — reached through ten test numbers. The documentation never states which status string a declined payment carries. Mapping declined to failed would be a guess wearing the clothes of a fact.

Refusing is the mechanism, not an inconvenience. The first real sandbox run against a declined test number will throw with the exact value in the message — and that message is the evidence needed to complete the map. A permissive default would convert that evidence into a silent assumption, and a payment status is not a thing to be silently assumed.

The real-sandbox suite is written to harvest exactly this: it drives every non-pending scenario and reports the value it received. Question K12 asks iPayMoney for the complete enumeration in parallel, because a sandbox may not exhibit every value a production account can.

Run #36 failed, and it was a real defect — in a test, not in the product

One browser test failed: delivery.spec.ts › the whole journey, then an unauthorized buyer tries everything. The webhook it posts answered 400 instead of 200. The same commit passed in run #37, which is exactly the shape of a race.

The cause: the test's buy() helper clicked pay and then waited for pay-waiting before reading the charge's provider_ref out of the database. pay-waiting is static text inside the form — it is on screen before the server action has done anything. So the read raced the charge being created, and when it lost, the webhook was posted naming an empty reference, which the route correctly refused.

This exact bug was found and fixed in checkout.spec.ts in an earlier phase, with a comment saying so. delivery.spec.ts is a second copy of the same journey and kept the old wait. It has now been corrected the same way — wait for payment-status to read pending, which appears only once the action has actually completed — and the helper now asserts the reference is non-empty, so a future race fails naming its cause instead of surfacing three lines later as an unexplained 400.

No product code changed. The application behaved correctly throughout: it refused a webhook that named no payment. Only the test was wrong, and only about when to look.

Reconciliation

reconcile-check.ts runs after the suite against the CI database and asserts the ledger reconciles: sum(direction × amount_minor) against the account_balances cache, plus the ten commerce detectors. It reported drift 0, 0 unbalanced transactions and a net of 0 XOF across 8 accounts, over a real capture → settlement → payout cycle. Both self-proving probes behaved: the commerce detector stayed silent on consistent data and raised succeeded_payment_orphaned when the gate broke it deliberately, and the refund detector stayed silent and raised refund_amount_mismatch. A detector that cannot be shown to fire is not evidence of anything, so the gate breaks its own invariants inside a rolled-back transaction on every run.

Why R7 and R8 survive, and why that is a finding rather than a hole

Three independent mechanisms serialise a refund dispatch: assertRefundTransition in application code, SELECT … FOR UPDATE on the refund row, and the guarded UPDATE … WHERE status = ?. Any one of them is sufficient to stop a double dispatch, so removing any one of them leaves behaviour unchanged and every test still passes.

That is what defence in depth means, and a surviving mutant here is the evidence that the depth is real rather than nominal. R26 exists to prove the tests are not simply blind: with all three removed, three tests fail. A reviewer should read R7 and R8 as "redundant, deliberately", and R26 as the assertion that the redundancy is the only reason they survive.

The harness itself was hardened during this milestone

A mutation escaped into a commit earlier in Phase 3: a killed run left the source mutated, and the next run captured the mutated file as its own backup. It was caught by reading a diff, not by a test.

The matrix now runs in a detached git worktree, not in the checkout, restores from a pristine snapshot keyed to that worktree, refuses to start against an already-mutated tree, and holds an flock so a second matrix cannot race the first. Both failure modes recurred while running this matrix — a killed run left R1 applied, and two matrices ran concurrently and recorded R1 twice with different counts — and both were caught by the new guards rather than by luck. The contaminated results were discarded and the matrix re-run clean from zero.
