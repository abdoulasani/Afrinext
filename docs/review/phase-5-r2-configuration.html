A

The eight answers, before implementation

All eight live in docs/providers/r2/README.md, written against Cloudflare's current documentation rather than memory. In brief:

Why R2, in one line

Egress is free. A catalogue whose product is repeated downloads pays its bill in egress, and on R2 that line is zero. The adapter stays S3-compatible regardless, so the decision costs four variables to reverse.

B

Two secrets, and what keeps them server-only

Only the access key and secret key are credentials. Three structural facts keep them out of a browser, and not one of them is a convention somebody has to remember:

  1. No NEXT_PUBLIC_ prefix. Next.js inlines a variable into client JavaScript only if its name starts with that. None do, so the bundler cannot put them in a browser bundle even by mistake.
  2. packages/core is never imported by a client component. The adapter is built in a route handler and a server action, and the eslint rule that forbids Next.js inside packages/* keeps that boundary from eroding.
  3. They are never logged. A test captures the process's actual stdout during two failed operations and asserts the key, the secret, AWS4-HMAC-SHA256 and Credential= are all absent from what was written.

The endpoint and bucket name are not credentials — useless without a token — but they stay out of pages and out of Git anyway, because naming your storage account is free reconnaissance. The browser test asserts neither appears in the library or product HTML, and it now reads the names from the configured bucket rather than the fixture's, so the assertion keeps meaning something on a real run.

The two new refusals, and why each is worth a guard

A plaintext endpoint. SigV4 signs a request; it does not encrypt it. Over http:// the Authorization header and the seller's files cross the network readable by anything on the path — and a typo that drops the s is not an error the adapter would otherwise notice, because it would work. Loopback is the only exception, on the literal addresses rather than the name localhost, which a hosts file can point anywhere.

An endpoint that is not a URL. This one was a live defect, found by a test I had written for something else. CONTENT_S3_ENDPOINT=example.com constructed cleanly, started the server, published the storefront, and would have failed at the first buyer's download — the exact failure shape this whole configuration path exists to prevent. It is parsed in the constructor now.

D

"Public access is disabled" as a test, not a screenshot

A dashboard screenshot is a claim about a setting somebody made once, on a console other people can also reach. This is the same claim expressed as a request that must be refused:

pnpm --filter @afrinext/core verify:storage

Against whatever CONTENT_S3_* is in the environment it writes one probe object, reads it back, and then fetches the object's URL with no Authorization header at all — exactly what a browser that guessed the URL would send. R2 must refuse. It probes the bucket root the same way, so a bucket that lists its contents is caught too. Then it proves a wrong secret is rejected, so the refusals mean the bucket enforced something rather than the script failing to reach a server that would have said yes. Finally it deletes the probe.

A connection error is a FAILURE, not a pass

The tempting shortcut — "the unsigned request didn't return 200, so we're private" — passes every misconfiguration that never reaches the provider at all. "Refused" and "could not connect" are different facts and the check reports them differently. Mutation S8 conflates them and dies.

The logic lives in packages/core/src/content/verify.ts rather than in the script, for two reasons. It can be pointed at a bucket that really is public — the test bucket has a publicReads mode for exactly this — and watched to say so; a safety check nothing has ever seen fail is one nobody knows the shape of. And it returns structured results and formats nothing, so the CLI decides what reaches a terminal, which is what keeps a credential out of the output.

The middle row is the one that matters, and note what still passed in it: the write, the read-back, the checksum, the content type. A round-trip test alone would have shipped that bucket.

E

Render: four values it must ask you for

render.yaml now names R2 and carries no credential. The endpoint, bucket, access key and secret key are declared sync: false — Render's marker for "set in the dashboard, not in this file" — the same posture DATABASE_URL and SESSION_SECRET already have. A value pasted into that file would be committed, pushed, and readable in git history forever, including after the line is deleted.

Two consequences you should agree to before the next deploy

1. The service will not start until you set them. That is the fail-closed behaviour working, not a regression — but it does mean the preview is down between this merge and your filling in those four fields.

2. The mounted disk is removed, and removing it deletes the volume. It existed only for filesystem storage. It also pinned the service to a single instance — Render will not run two of a service that has a disk — which would have made the multi-instance guarantee untestable on the very deployment meant to demonstrate it. The volume holds preview uploads only, and those do not survive the move to a bucket. A production service with real files would migrate the objects first.

H

What I need from you, exactly

Nine steps, and only the first six need a person. They are in docs/providers/r2/README.md too, so they do not live only in this PDF.

  1. Create a Cloudflare account for AFRI NEXT TECHNOLOGIE and enable R2.
  2. Create bucket afrinext-content-prod. Pick a jurisdiction deliberately if data location matters — the endpoint changes if you do.
  3. Confirm Public access → r2.dev subdomain: Disabled, and no custom domain connected.
  4. Leave CORS unset. There is nothing to configure.
  5. Create an R2 API token, permission Object Read & Write, scoped to that bucket only. Copy the Access Key ID and Secret Access Key — Cloudflare shows the secret once.
  6. Repeat 2–5 for afrinext-content-preview, with its own token. A leaked preview credential must not reach a real seller's file.
  7. Set the four values in Render → Environment. The other three come from render.yaml.
  8. Run verify:storage against the bucket. It must end ALL CHECKS PASSED.
  9. Run the journey against it: E2E_REAL_BUCKET=yes pnpm test:e2e.
How to give me the credentials, if you want me to run 8 and 9

Put them in the environment, not in a message and never in a file I commit — the same way DATABASE_URL already reaches this session. If you would rather run those two commands yourself, that is the safer choice and the output is short enough to paste back. Either way I will not have written a credential into the repository.
